# Drop

Drop is a mobile-first way to send a friend a photo, meme, GIF, or personal note as a private drop. Sending is instant by default; a human relay is an optional journey.

The append-only engineering learning log is in [LEARNINGS.md](./LEARNINGS.md); it records solved issues, causes, verification evidence, and Git checkpoints.

## Run locally

```bash
npm ci
./run.sh
```

Open `http://localhost:4004`. Run `./run.sh` again to restart Drop, or `./run.sh stop` to stop it. Without Supabase credentials, the app runs with local demo data. Real account-to-account media delivery needs the Supabase migrations and private storage setup in [SUPABASE_SETUP.md](./SUPABASE_SETUP.md). Hosted Drop provisioning is currently waiting on project-creation access; no Drop project has been created.

The local Supabase backend runs in Docker through the Supabase CLI (`npm run supabase:start`); the Next.js app runs as a local Node process through `run.sh`. The main local endpoints are app `4004`, Supabase API `54321`, Studio `54323`, and Mailpit `54324`. Use `npm run supabase:stop` to stop this project's local Supabase stack.

## Private unread state

For delivered drops addressed to the signed-in recipient, the inbox shows a “New” marker and Inbox navigation count until the full drop opens successfully. The server stores read markers privately for that recipient; senders cannot see them. The local migration and API are covered by `npm run test:local-supabase` and the rollback-only `tests/db/drop_recipient_read_state.sql` fixture.

To run the authenticated browser smoke, start the local Supabase stack and keep `.env.local` configured with the local CLI URL, anon key, and service-role key, then run `node scripts/browser-unread-smoke.mjs`. It verifies sign-in, read/open behavior, and persistence after reload at mobile 390×844 and desktop 1440×900. It requires free test port 5004 (the isolated app port mapped from main port 4004) and an installed Chrome or Edge browser. The script creates and removes disposable local accounts and a drop; it rejects a non-loopback Supabase URL and does not use hosted Supabase.

To verify the complete local text-drop loop, run `node scripts/browser-send-react-smoke.mjs` with local Supabase running and the same loopback-only `.env.local` values. It builds an isolated production app with `next build --webpack` and runs it on port 6004 with `next start`. Three isolated browser profiles cover the sender and two sessions for the same recipient: the smoke sends from Compose, checks unread state at 390×844 and 1440×900, opens and reacts, then verifies the second recipient session clears “New” from the next server refresh without reloading. It also checks the sender's live and reloaded reaction and removes the exact disposable drop, reaction, accounts, profiles, app, and browser profiles. It rejects non-loopback Supabase URLs and never passes the service-role key to browser code. This exercises local text sending and reaction behavior, not hosted delivery or media claims.

## Share an image to Drop

On a compatible browser where Drop is installed, choose Drop from the system share sheet to start a draft from one JPEG, PNG, WebP, or GIF (up to 8 MB) and an optional caption. The service worker stores the handoff in browser IndexedDB for up to one hour; opening it creates an unsent local draft. Nothing is sent until the sender uses the normal send flow. If the service worker is not controlling the page, the browser has already submitted the share request to the site before the fallback can explain the problem; use the in-app photo picker when you need to avoid that fallback.

Relay passports count carrier handoffs only; the metric is labeled consistently as **Carriers**, and its actions and headline wrap for narrow screens.

Reaction buttons expose text labels such as “React with heart hands” to assistive technology instead of relying on emoji pronunciation.

With Drop running on port 4004, run `node scripts/browser-demo-smoke.mjs`. The smoke opens an isolated temporary Chrome/Edge/Chromium profile and checks complete GIF flows at 360×844, 390×844, 430×844, and 1440×900, plus a photo flow at 390×844. It uses touch at 360px and keyboard activation at 390px, 430px, and desktop. The no-handle choice, its “anyone with the link can claim” disclosure, account gate, focus return, and saved-claim recovery/detail copy are checked with keyboard at all four widths. Home and the chooser are checked for horizontal overflow at all widths. Use `node scripts/browser-demo-smoke.mjs http://127.0.0.1:4004 --claim-recovery-only` for handleless-choice and seeded recovery flows, or `--prompt-only` for the Home writing-spark flow. The page-scoped request gate checks for cross-origin, Auth, REST, RPC, and Storage-write requests; these local checks do not validate hosted sends, server-side activity, screen readers, or physical devices. Chrome touch input timed out at 430px in this environment, so that viewport uses the tested keyboard path.

Use `node scripts/browser-demo-smoke.mjs http://127.0.0.1:4004 --friend-draft-only` for the sender-copy → fresh composer keyboard flow at 390×844. It checks a blank text draft, the same-device unsent notice, top-of-page landing, and preservation of a prior photo draft and its IndexedDB bytes. Run browser smoke against an isolated app copy without `.env.local` when the working checkout has hosted Supabase credentials: the test browser blocks cross-origin auth requests, so it cannot establish an account session. This focused flow does not verify hosted sending.

To save optional screenshots, set `DROP_BROWSER_SCREENSHOT_DIR` to a new empty folder outside the repository before running the smoke. The focused mode captures Home, sender copy, the CTA, and the new composer; the full mode captures the 390px and desktop GIF journeys and recovery states without adding images to Git.

The composer shows account readiness and recipient selection before the note, photo, or GIF controls. From an empty recipient step, **Share without a handle** lets the recipient sign in or join and claim without the sender knowing a handle; new recipients choose one during setup. This creates a bearer link that anyone holding it can claim, so the composer calls that out before sharing; a connected account and saved payload are still required. The sender can return to handle entry, and focus moves to the newly shown control. Recipient lookup and invite detours preserve the existing local draft. Each invite outcome (shared, copied, cancelled, or unavailable) is saved with that account’s draft so the composer and mailbox can offer the right next step; a manual-copy link remains available after an unsuccessful retry. If a private claim link was prepared but not shared, Compose says so and keeps a copy action. After recovery or reload, **Open saved drop** goes to that drop’s detail page for claim status or a fresh link. Progress clears when the handle resolves or changes, or when the drop is sent. Send receipts are tied to the submitted draft content, so edits made in another tab stay drafts.
When sign-in returns to a guest draft, Drop copies it into the signed-in account and verifies the account-scoped draft before opening Compose. If the transfer, readback, or account check fails, the callback keeps the user on profile recovery with a retry/check-again path and the guest copy intact.
The auth callback shares a pending one-time PKCE code exchange across React effect replay. A disposed callback run cannot redirect or update its state after a newer run takes over.
Before sharing an invite, Drop confirms the current draft was written to local storage. On the invite profile’s final step, people can open the share sheet or explicitly copy their public handle and profile link. If clipboard access is denied, selectable text provides a manual fallback; cancelling the share sheet does not copy automatically.

Mailbox empty states now respond to the selected filter and offer a matching next step; clearing a search keeps the selected filter and returns focus to the search field.

Home’s **Use this thought** action opens a fresh text drop with the displayed writing prompt already in the editable composer. It starts a separate draft by ID, so an unfinished photo/GIF draft and its local attachment remain available. The prompt itself is not placed in the URL.

For an unknown handle, or when the sender explicitly chooses the handleless route, the composer can share a private claim link for an instant text, photo, or GIF drop; relay claim links are not part of this flow. A handleless claim link is a bearer link that anyone holding it can claim. The recipient signs in or joins Drop, then explicitly claims the drop before its content or media is released. The shared link carries the bearer token in the URL fragment, never in query parameters or share copy, and the page removes it from the address after arrival. To resume sign-in in another tab of the same browser, Drop temporarily stores the token in browser local storage for up to 10 minutes and passes only a random opaque handoff ID through profile/auth-return URLs. The receiving tab saves the token in its own session storage before removing the shared copy. If tab storage cannot save it, the shared record remains available until expiry. The open tab schedules cleanup; expired or malformed records are also removed on the next claim-page load. A successful claim clears any remaining handoff. This transfer does not move between browsers or devices, which must reopen the original invite. The sender sees a waiting state and can rotate the link from the sent-drop page; a fresh link replaces the old one. A successful claim updates an open sender detail page live; the result also appears as “Claimed by [name]” in Sent and on the detail page after reload. The sender-only status RPC returns claimed drop IDs without exposing invite tokens or recipient account IDs. Claim links expire after 7 days. Unclaimed photo/GIF claims and media access end 30 days after the initial send; rotating a link does not extend that deadline. The hourly worker queues expired objects for deletion through the Supabase Storage API and retries failed removals. It also scans up to 25 finalized objects per run that are older than 30 days and unlinked when initial queue attempts failed, plus up to 25 valid unlinked `/pending/` staging uploads that have been in Storage for 30 days. Pending-file removal uses the Storage API, retries failures, blocks a queued path from re-upload, and keeps a completed-path tombstone for at least 24 hours. A paused Free project or a Storage/worker outage can delay physical deletion after the access cutoff. Apply `20261023120000_drop_claim_invites.sql`, `20261023130000_drop_claimed_sender_broadcast.sql`, `20261023140000_sender_claimed_drop_status.sql`, `20261023150000_private_media_claim_invites.sql`, `20261023160000_reconcile_orphan_drop_media.sql`, and `20261023170000_drop_pending_media_retention.sql` in order before deploying the updated cleanup worker. Configure the cleanup worker and Vault secrets as described in [SUPABASE_SETUP.md](./SUPABASE_SETUP.md). A disposable PostgreSQL policy fixture is available at `tests/db/drop_claim_invites.sql`.

The cleanup scans read managed Storage metadata in ordered cursor pages and do not add custom indexes to `storage.objects`. Supabase assigns Storage objects to `supabase_storage_admin` and restricts index creation on existing managed-schema tables ([permissions](https://supabase.com/docs/guides/platform/permissions), [managed-schema restrictions](https://supabase.com/changelog/34270-restricting-access-on-auth-storage-and-realtime-schemas-on-april-21-2025)). The page size limits candidates per run, but scan/sort cost can rise as the bucket grows; large-bucket performance has not been measured.

The private-claim sent receipt distinguishes a finished share sheet from a copied link and does not claim the recipient received or opened it. Waiting and claimed labels use the sender’s saved drop and claim-status check. A missing or stale receipt ID never falls back to showing another local draft.

After a recipient saves a new handle, Drop returns them to the private claim page only after account sync succeeds. The final **Claim this drop** button remains explicit; Drop never claims or reveals the content automatically. The compact progress indicator and concise privacy/expiry summary bring the next action higher on small screens. If the browser cannot persist the invite for sign-in, the page stays open and explains how to recover without putting the bearer token in a route.

If a claim check hits a temporary service error, Drop keeps the invite in the current tab and offers a retry; terminal/unavailable responses keep generic fresh-link guidance. The user-facing message never includes raw database errors or the invite token.

The cleanup endpoint's HTTP, secret, and configuration boundary is covered by `tests/dropMediaCleanupEndpoint.test.mjs`, using a fake Supabase client to prove rejected requests make no privileged calls. These Node tests do not validate Deno bundling, hosted worker configuration, or actual Storage deletion.

## Relay retry recovery

Carrier invite accepts keep the exact attempt details in the current browser tab for up to 24 hours. If the response is interrupted, refresh the same invite in that tab and choose “Retry same handoff”; Drop clears the record after the carrier pass is saved.

When a connected sender has confirmed that a recipient handle is not on Drop, Relay mode offers **Switch to Instant for a private link**. The switch keeps the current draft and saved media, then focuses the existing private claim-link action. It does not send or share anything until the sender explicitly chooses that action. Relay claim links remain unavailable.
